# PaymentService

OrchestrPay — стартап, разрабатывающий собственную платёжную платформу, которая должна работать как с розничными клиентами (B2C), так и с партнёрскими компаниями (B2B). Ключевой бизнес-процесс — обработка платежа на маркетплейсах с проверкой в антифрод-системе и внешних сервисах.

## Структура репозитория

### [Task1](./Task1/)
Проектирование шагов Saga-оркестрации. Анализ транзакций, задействованных в процессе обработки платежа, определение их типов (компенсируемая/необратимая/повторяемая) и компенсирующих транзакций.

**[Таблица-реестр транзакций Saga-оркестрации](./Task1/result.md)**

### [Task2](./Task2/)
Применение State Machine на практике. Создание таблицы переходов, отражающей все возможные состояния платежа и события, которые переводят его из одного состояния в другое.

**[Таблица переходов состояний](./Task2/result.md)**

### [Task3](./Task3/)
Архитектурное решение о размещении оркестратора. ADR (Architecture Decision Record) с анализом вариантов размещения функции оркестрации — внутри одного из доменных сервисов или в отдельном сервисе-оркестраторе.

**[Размещение оркестратора платёжной саги](./Task3/result.md)**

### [Task4](./Task4/)
Создание BPMN-диаграммы процесса обработки платежа с использованием Camunda Modeler. Диаграмма отражает как успешные, так и компенсационные развилки, включая шаг с возможным ожиданием ответа после ручной антифрод-проверки.

**[BPMN-диаграмма процесса](./Task4/diagram.png)**

### [Task5](./Task5/)
Описание тест-кейсов для проверки корректности работы системы. Таблица интеграционных и end-to-end тестов, покрывающих основные и граничные случаи.

**[Таблица тест-кейсов](./Task5/result.md)**
